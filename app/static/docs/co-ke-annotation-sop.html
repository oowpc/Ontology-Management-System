0. 目的与适用范围

本 SOP 规定 CO/KE 手工标注从准备、双盲标注、逐题对齐、本体合并、GOLD 合并、跨组复核到入库的统一流程与验收口径。返工、回溯和异常处置另见《CO/KE 标注返工 SOP》。

适用对象包括五类数据集：政策与业务 Query、CO/KE 标注数据集、SQL Query 数据集、LEAN 定理/证明 Query 数据集、SPARQL Query 数据集及其人工确认结果。SQL、LEAN、SPARQL 均以一个 query 或证明目标及其结构化结果作为核心标注对象，字段与可执行性校验分别定义，不与 CO/KE 字段硬套。纯机器生成、未经人工确认的结果不得标记为已通过。

1. 标注单元

为避免“条数”口径混乱，必须区分三层：

  • 来源单元：一篇文章、一个政策文件、一个数据集条目或一个 Query。
  • 标注单元：从来源单元中切出的、可独立判定的问题或事实单元，必须有唯一 ID。CO 与 KE 都以标注单元为单位，同一 ID 在整条链路中不变。
  • 原子结果：一个标注单元中的一个 Concept、Constant、Variable、Operator、Rule、Method/Step，或一条 KE 断言。

默认统计单位是“标注单元”；结构性错误另按原子结果统计。批次记录必须写明本批采用的统计单位，不得把来源单元、标注单元和原子结果混为一谈。

2 Query 数据集的标注单元

SQL、LEAN、SPARQL 数据集的默认标注单元，是一个独立的自然语言 Query 或证明目标，以及与之对应的结构化结果。批次记录还必须写明数据集方言、版本和执行环境。

  • SQL：自然语言问题、数据库 schema、目标 SQL、参数/实体映射、执行结果或结果集语义。SQL领域可以脱离题目建设本体，并且可以参考对应的GOLDSQL，如果有的话
  • LEAN：数学领域的大本体已经提前建好，标注时只需要写KE即可。
  • SPARQL：自然语言问题、RDF/OWL 图谱或 schema、目标 SPARQL、变量与三元组模式。可以参考GOLDSPARQL。

三类数据集共用“有证据、可追溯、保留原始结果、人工复核”的原则，但结构字段与可执行性校验必须分别记录，不得用 CO/KE 的字段一致率替代领域校验。

3. 组织形态：两人一组，跨组复核

3.1 基本单元

  • 标注组：固定 2 名标注者（记为 A、B），共同完成一个批次。两人地位对等，不存在“主标”和“辅助”。
  • 交叉检查组：另一组的至少 2 名成员，独立复核本组的大本体与全部 GOLD KE。
  • 同一人不得同时是本组标注者和本组交叉检查者；交叉检查组不得把本组中间结果当“参考答案”，只复核最终产出。

3.2 角色

  • 标注者 A / B：独立完成每道题的 CO，共同完成逐题对齐与大本体合并，独立完成 KE，参与 GOLD 合并并执行修改。
  • 组长（可由 A 或 B 兼任）：只负责排期、冻结与解锁、留痕完整性和 issue 登记，不代替另一方做判定。
  • 裁决人：处理两人无法达成一致、且无法由客观证据直接判定的分歧。
  • 批次负责人：维护批次记录、版本与指标。
  • 项目负责人：批准发布、返工定级与回溯范围。

3.3 双盲与隔离

  • CO 阶段：A 与 B 各自独立标注，任何人不得查看对方的 CO 结果、草稿或讨论记录。逐题对齐开始后，两人共享彼此该题的 CO，但仍不得提前查看后续题目的对方结果。
  • KE 阶段：两人使用同一份已冻结的大本体，但各自独立标注，不得查看对方的 KE。
  • 隔离必须由工具或流程实现：不同目录或数据集副本、权限隔离、提交后才解锁。只靠“自觉不看”不算隔离。
  • 唯一允许共享的输入：冻结后的数据集、指南、模板、术语表、已裁决的 issue 结论。
  • 提前共享视为流程违规，按第 6 章登记 issue，并评估该批次结果是否需要重标。

3.4 状态机

草稿 → 数据集冻结 → CO 双盲中 → CO 逐题对齐中 → 本体合并中 → KE 双盲中 → GOLD 合并中 → 交叉检查中 → 待校验 → 已通过。

任何环节发现问题进入“返工中”；返工结束后回到对应环节，不得直接跳到“已通过”。

4. 标准流程（八阶段）

4.1 阶段 0：准备

本阶段的唯一目标，是把输入冻结成 A、B 与交叉检查组都能复现的同一份东西。准备不完成，不得开始标注。

数据集冻结

  • 记录数据集名称、版本号或 commit、来源、授权范围、总条数、切分方式。
  • 生成清单文件并计算校验和（如 sha256），A、B 使用同一份副本。
  • 检查重复题、训练/测试污染、空题、超长题；异常条目单列并说明处置。
  • 每条必须有稳定的标注单元 ID，且与后续 CO、KE、GOLD 记录一一对应。

英文数据集的中文翻译

  • 英文数据集必须提供中文翻译，并与原文逐条对齐存放；翻译是标注的必需输入，不是可选项。
  • 译文与原文冲突时以原文为准；冲突条目必须登记 issue，不得由标注者自行取舍后继续。
  • 翻译不得加入原文没有的条件、主体、时间或数值；发现机翻补全内容即按关键错误处理。

evidence 准备

  • 有 evidence 的数据集，必须把 evidence 随标注单元一起准备好：来源 ID、定位（文档/页码/段落/字符偏移）、原文片段、语言。Query 类数据集以 schema/图谱/环境快照作为证据。

模板与环境

  • 统一模板：逐题 CO 表、CO 对齐记录表、大本体清单、KE 表、GOLD 记录表、issue 表、交叉检查表。
  • 建立批次记录：批次号、来源范围、统计单位、指南版本、A/B、交叉检查组、预计规模、验收门槛。
  • 开始标注前两个标注者需要阅读本文档以及，

准出条件：数据集已冻结并有校验和；翻译与 evidence 齐备或已登记缺口；模板与环境已固定；批次记录已建立。完成后状态为“数据集冻结”。

4.2 阶段 1：两人分别独立标 CO（双盲）

  • A、B 各自对每道题（每个标注单元）标注 CO：概念、常量、算子，或明确判定不收录。
  • 每条 CO 必须带证据、判定理由、标注者、指南版本、时间戳。
  • 两人不得交流标注思路，不得查看对方的 CO 文件或草稿。
  • 发现指南缺口或数据问题，登记 issue 并继续标注其余题目；不得为绕开缺口自行发明规则，也不得私下对齐口径。

产出：CO_A[i] 与 CO_B[i] 两套逐题结果，题目覆盖本批全部标注单元。

4.3 阶段 2：两人逐题对齐 CO

逐题对齐是本版流程的关键环节：先把“每道题的 CO 该长什么样”谈成一致，再谈“整个本体长什么样”。

  • 按标注单元 ID 顺序逐题进行。每题同时展示 A 与 B 的 CO，两人对照原文证据逐项确认：
  • 概念是否收录、是否不收录；
  • 粒度是否一致（同一事实不拆成两条、也不合成一条过粗的）；
  • 命名是否指向同一含义；
  • 类型与角色是否正确；
  • 关系两端的类型与方向是否成立。
  • 每题产出一个对齐结论 CO_ALIGNED[i]，并记录：
  • 双方原始条目（引用 CO_A[i]、CO_B[i] 的条目 ID）；
  • 分歧点与分歧类型（收录与否 / 粒度 / 命名 / 类型 / 父类方向 / 其他）；
  • 处理方式（一致 / 取 A / 取 B / 合并 / 拆分 / 均不成立重标 / 待裁决）；
  • 理由与证据、决定人、时间。
  • “一致”不等于“文字相同”。同义不同名、同义不同粒度的，必须在本题内判定清楚，不得留给后面合并阶段含糊处理。
  • 无法在本题内达成一致的，登记 issue 并在 CO_ALIGNED[i] 中标注“待裁决”，继续下一题；不得因为一题卡住就中断整批，也不得强行折中。
  • 对齐阶段只处理单题内的口径，不做跨题去重与父类设计——那是下一阶段的事。
  • 对齐结束后输出覆盖率：已对齐题目数 / 全部题目数，未对齐题目必须逐条说明原因。

产出：逐题 CO 对齐记录表、CO_ALIGNED 全集、分歧清单与遗留 issue。

4.4 阶段 3：两人一起合并成大本体

  • 基于 CO_ALIGNED 全集，两人共同构建唯一主大本体 CO_M，不再各自先造一套再比对：
  • 跨题去重：同一概念在多个题目中出现时合并为一个，保留来源题目映射；
  • 统一命名与类型，建立命名规范与别名记录；
  • 为每个概念确定父类，父类缺失时显式标记待定；
  • 核对算子签名：主体、参数、返回类型齐全，避免同名不同义。
  • 合并过程必须留痕：每合并一组概念，记录合并了哪些来源条目、由谁提出、理由是什么；拆分的同样记录。
  • 合并完成后做回查：逐题核对 CO_ALIGNED[i] 中引用的每个概念都能在 CO_M 中找到，且语义未在合并中被改变；发现偏差回到该题重新对齐。
  • CO_M 必须可导入、可校验：父类存在、无循环继承、无重复定义、算子主体与返回类型齐全。通过校验后冻结并升版（如 v1）。
  • 遗留的“待裁决”概念在 CO_M 中保留标记，裁决后统一升版，不得静默补写。

产出：CO_M v1、概念来源映射表、合并与拆分日志、回查记录、遗留 issue 清单。CO_M 冻结后才能进入 KE 阶段。

4.5 阶段 4：两人以同一大本体分别标 KE

  • 以冻结的 CO_M 为唯一本体依据，A、B 各自对每道题标 KE。
  • KE 中引用的概念必须已存在于 CO_M。需要新概念时提 issue 申请扩展，经确认后统一升版，不得在 KE 里私自引入。
  • 两人独立标注，互不可见；每条 KE 附证据、推理依据、自检结果（语法、类型、父类、引用）。
  • SQL、LEAN、SPARQL 数据集需额外记录执行或编译结果与环境版本，作为可执行性证据。

产出：每道题两份 KE——KE_A[i] 与 KE_B[i]，共 2N 条，全部带 ID 与版本。

4.6 阶段 5：合并出 GOLD KE

  • 所有题标完后，两人一起逐题比对 KE_A[i] 与 KE_B[i]，给出该题的 GOLD 结论，且必须限定为以下四种之一：
  • 等价，取其一（写明取 A 还是 B）；
  • 择一更优（写明另一条错在哪里）；
  • 合并修改为新 KE（写明修改点与理由）；
  • 两条都不成立，重标（写明原因，重标后重新比对）。
  • 每条 GOLD KE 记录：来源（A / B / 合成 / 重标）、差异点、判定理由、决定人、时间。
  • GOLD 阶段如果需要新概念或改父类，回到 CO_M 走 issue 与升版流程，不得在 KE 里私建。
  • 同一道题多次往返仍未定的，登记 issue 交裁决人，不得挂起后直接跳过。

产出：GOLD KE 全集、逐题 GOLD 决议记录、GOLD 版本号。

4.7 阶段 6：另一组交叉检查

  • 交叉检查组（≥2 人）独立复核三样东西：主大本体 CO_M、逐题 CO 对齐记录、全部 GOLD KE。
  • 本体检查项：重复与同义概念、孤立概念、父子关系错误、命名与类型一致性、算子主体与返回类型、是否覆盖本批所有标注单元引用的概念。
  • 对齐记录检查项：是否每题都有对齐记录、分歧是否写明类型与理由、是否存在“看起来一致实际粒度不同”的情况、待裁决项是否都有 issue。
  • GOLD KE 检查项：证据是否支撑结论、类型与父类是否正确、语法与引用是否通过、Query 类是否在指定环境可执行、是否存在凭空补全、是否存在未登记的口径扩展。
  • 交叉检查组只出结论，不改文件。结论分三种：通过；需修改（逐条列 ID、问题、证据、建议）；阻断（存在关键错误或系统性风险）。
  • 修改由原标注组执行，改完再由交叉检查组复检，至少形成一轮完整闭环记录。交叉检查组不得代改；原标注组也不得只改被点名条目而不检查同类问题。

产出：交叉检查报告、问题清单、复检记录、结论（通过 / 需修改 / 阻断）。

4.8 阶段 7：校验、发布与归档

  • 完成三类校验：人工证据校验、结构校验、执行器/导入器校验。
  • 记录入库前后数量与关键字段，回读核对。
  • 归档：冻结数据集与校验和、翻译版本、evidence 清单、CO_A / CO_B、逐题对齐记录、CO_M 各版本、KE_A / KE_B、GOLD KE、合并日志、全部决议、issue 记录、交叉检查报告。

5. 全过程留痕

5.1 必须留痕的六类记录

  • 输入：数据集版本与校验和、翻译版本、evidence 清单、指南与模板版本。
  • 双盲过程：A、B 各自的逐题 CO 与 KE 原始文件及提交时间，用于证明隔离有效。
  • 对齐与合并过程：逐题对齐记录、分歧处理理由、本体合并与拆分日志、回查记录、GOLD 逐题决议及理由。
  • 检查过程：交叉检查报告、问题清单、复检记录。
  • 变更过程：每次修改的字段、原值、新值、理由、操作人、时间、影响的版本。
  • 发布过程：校验结果、入库记录、回读结果、发布批准人。

5.2 不可覆盖

  • 原始结果、被修改前的值、复核意见、裁决记录一律只读保留，新增版本另存并关联原条目 ID。
  • 不得用“最终版覆盖历史版”的方式留痕；不得事后补写时间或理由冒充当时记录。
  • 记录必须能回答：谁、什么时候、基于哪个版本、改了什么、为什么改、谁批准的。

6. Issue 管理

本节口径对齐《入口组 KE/CO 问题 issue 整理》的实际台账，并规定 issue 的解决层级：组内两人 → 组长 → 技术讨论会。

6.1 分类与标题格式

标题统一写成：IssueN：【一级分类】【二级标签】一句话说清问题。

一级分类沿用实际台账，不另造同义类目：

  • 建模
  • KE 写法
  • 是否有必要用 KE 推理
  • 本体格式与元数据
  • 流程与规则抽取
  • 理解与词义
  • 问题分类与判据
  • 数据与证据
  • 工具与平台

二级标签按实际使用持续补充，同一含义只用一个标签。已有示例：动作的状态语义翻译、method 写法、meta level 建模、定义类问句、Why/How 建 KE 条件、单位与量纲、一词多义、命名与释义、source/description、三档边界、黑盒算子语义、多条件判定、抽象层级、不适合用 KELE 解决、不适合用 KE+NL 模糊。

6.2 必填字段

  • 编号与标题（含两级分类标签）。
  • 重要性、紧急性：分别评高/中/低，不合并成一个“优先级”；两者都高的问题优先上会。
  • 提出人、提出时间、发现阶段、关联批次与标注单元 ID。
  • 问题描述：先用一句话说清，再展开背景。
  • 例题：原文、evidence、期望结果与当前实际结果。
  • Cases：至少 2 个，覆盖边界情况，不能只举一个孤例。
  • 需要讨论的问题：拆成可判定的问句，一条一问，避免“如何更好地建模”这类无法回答的表述。
  • 各方观点：谁、什么立场、理由是什么；观点不等于结论。
  • 当前结论、状态、解决层级、责任人、时限。
  • 关联版本：指南版本、CO_M 版本、GOLD 版本、方言或工具版本。

6.3 解决层级：组内两人 → 组长 → 技术讨论会

L0 组内（A、B 两人）

  • 适用范围：单题口径、命名、粒度、是否收录、证据认定。
  • 做法：先对照原文和指南自查；两人当面逐条讨论，结论必须写回 issue，并同步到该题的 CO/KE 记录。
  • 时限：当日给出结论或升级。
  • 禁止：用“两人都同意”代替证据；口头结论不留痕；顺手改数据。

L1 组长

  • 适用范围：组内无法一致；需要在一批内统一口径；同类问题涉及 2 题以上；对指南理解有分歧但不需要改指南。
  • 做法：组长在 1 个工作日内裁决，写明依据（原文条款、指南条款或已有 issue 先例）；裁决在本组内有约束力，并沉淀为 FAQ 条目供后续批次直接引用。
  • 影响面：组长负责划出受影响的题目范围，交标注组回查同类问题。
  • 时限：1 个工作日；超时升级。

L2 技术讨论会

  • 适用范围（满足任一）：影响标注方法论（method 写法、meta level 建模、状态语义、算子设计）；需要修改 KE 方言、语法或校验规则；本体结构规则（父类、多父类、抽象层级）；指标与验收口径；跨组或跨批次争议；指南需要升版；工具缺陷造成系统性阻塞；同一问题在 2 个及以上批次重复出现。
  • 提交要求：提案人提前 1 个工作日提交材料包——问题描述、至少 2 个 Cases、各方观点、候选方案（至少 2 个并说明取舍）、影响面（涉及题目数、批次、已发布数据）。
  • 产出：决议编号、结论、责任人、落地时间、影响面处置方案。结论回写 issue，并同步修订指南、本体或模板后升版。
  • 约束：未上会不得按个人理解批量改标；会议未决的 issue 保持“讨论中”，相关题目状态标“待裁决”。

升级与时限

  • 不得跳级；紧急情况可并行上报，但必须同时告知组长并在 issue 中记录。
  • L1 超过 2 个工作日未决、或 L2 连续两周未排期，上报项目负责人。
  • L2 决议与现行指南冲突时，以决议为准，并立即升版指南；受影响的历史批次按返工 SOP 的 L4 影响面评估处理。

6.4 处理规则

  • 不得擅自修改：发现问题的任何一方，都不得直接改动对方或被复核的结果，不得静默修补，不得口头达成一致后不留记录。
  • 修改必须走流程：登记 issue → 判定影响面 → 由有权修改的人执行 → 留痕 → 复检 → 关闭。
  • 一个 issue 只设一个责任人；结论必须可执行，写清改哪个版本、改哪些条目。
  • 关键语义问题、双盲被破坏、未登记修改，一律先冻结相关范围，再定级。
  • 同一 issue 涉及多批次时，按返工 SOP 的 L4 影响面评估处理。

6.5 状态与关闭

  • 状态：未解决 → 讨论中 → 待落地 → 已解决。重复的标“并入 #N”，不处理的标“不处理”并写明理由。
  • 关闭必须写明：结论、依据、影响范围、落地动作（改了哪个版本）、复检结果。
  • 不得以“已沟通”“会上说过”关闭；未落地就关闭视为未关闭。

6.6 统计与复盘

每批复盘统计：未解决数、按一级分类分布、L0/L1/L2 各层占比、平均关闭时长（分层统计）、重复 issue 率、因 issue 阻塞的题目数、上会决议落地率。上行指标异常的，优先修指南或流程，不把系统性问题记成个人失误。
